<Badge color="green">OSS</Badge> <Badge color="red">Enterprise</Badge> Hybrid search is available in OSS and Enterprise.

Hybrid search combines vector similarity with keyword matching. It is useful
when a query needs both: for example, finding products with a particular model
number whose descriptions match what the customer is looking for.

LanceDB runs a vector search and a full-text search, then merges their results
with a reranker. Reciprocal Rank Fusion (RRF) is the default. It combines the
positions of records in the two ranked lists.

Before you query, store vectors and create an FTS index on the text column.

<span id="run-a-hybrid-query-with-explicit-vectors"></span>

<Accordion title="Run a complete hybrid search example">

These examples use three sample records and hand-written vectors, so no
embedding service is needed. Each program creates a temporary local table
and removes it when finished.

- **Python:** Install with `pip install lancedb`, save as `hybrid_search.py`, then run `python hybrid_search.py`.
- **TypeScript:** Install with `npm install @lancedb/lancedb`, save as `hybrid_search.mts`, then run `node hybrid_search.mts` with Node.js 22.18 or later.
- **Rust:** Download and extract the [complete Rust examples](/enterprise/v8-1-0/static/code/search-rust.zip), then run `cargo run --locked --bin hybrid_search` from the extracted directory.

<CodeGroup>
```python Python icon="python"
from tempfile import TemporaryDirectory

import lancedb
from lancedb.index import FTS

with TemporaryDirectory(prefix="lancedb-search-") as uri:
    db = lancedb.connect(uri)
    table = db.create_table(
        "documents",
        [
            {
                "id": 1,
                "text": "A puppy playing in the park",
                "category": "animals",
                "vector": [1.0, 0.0],
            },
            {
                "id": 2,
                "text": "A dog resting at home",
                "category": "animals",
                "vector": [0.9, 0.1],
            },
            {
                "id": 3,
                "text": "A guide to growing tomatoes",
                "category": "gardening",
                "vector": [0.0, 1.0],
            },
        ],
    )
    from lancedb.rerankers import RRFReranker

    table.create_index("text", config=FTS())
    rows = (
        table.search(
            query_type="hybrid", vector_column_name="vector", fts_columns="text"
        )
        .vector([1.0, 0.0])
        .text("puppy")
        .rerank(RRFReranker())
        .limit(2)
        .to_list()
    )
    print(rows)
```

```rust Rust icon="rust"
use arrow_array::types::Float32Type;
use arrow_array::{FixedSizeListArray, Int64Array, RecordBatch, RecordBatchIterator, StringArray};
use arrow_schema::{DataType, Field, Schema};
use futures::TryStreamExt;
use lance_index::scalar::FullTextSearchQuery;
use lancedb::index::{Index, scalar::FtsIndexBuilder};
use lancedb::query::{ExecutableQuery, QueryBase};
use std::sync::Arc;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let directory = tempfile::tempdir()?;
    let db = lancedb::connect(directory.path().to_str().unwrap())
        .execute()
        .await?;
    let schema = Arc::new(Schema::new(vec![
        Field::new("id", DataType::Int64, false),
        Field::new("text", DataType::Utf8, false),
        Field::new("category", DataType::Utf8, false),
        Field::new(
            "vector",
            DataType::FixedSizeList(Arc::new(Field::new("item", DataType::Float32, true)), 2),
            true,
        ),
    ]));
    let batch = RecordBatch::try_new(
        schema.clone(),
        vec![
            Arc::new(Int64Array::from(vec![1, 2, 3])),
            Arc::new(StringArray::from(vec![
                "A puppy playing in the park",
                "A dog resting at home",
                "A guide to growing tomatoes",
            ])),
            Arc::new(StringArray::from(vec!["animals", "animals", "gardening"])),
            Arc::new(
                FixedSizeListArray::from_iter_primitive::<Float32Type, _, _>(
                    [[1.0, 0.0], [0.9, 0.1], [0.0, 1.0]]
                        .into_iter()
                        .map(|v| Some(v.into_iter().map(Some).collect::<Vec<_>>())),
                    2,
                ),
            ),
        ],
    )?;
    let reader = RecordBatchIterator::new(vec![Ok(batch)].into_iter(), schema);
    let table = db
        .create_table(
            "documents",
            Box::new(reader) as Box<dyn arrow_array::RecordBatchReader + Send>,
        )
        .execute()
        .await?;
    table
        .create_index(&["text"], Index::FTS(FtsIndexBuilder::default()))
        .execute()
        .await?;
    let query = table
        .vector_search(&[1.0_f32, 0.0])?
        .full_text_search(FullTextSearchQuery::new("puppy".into()).with_column("text".into())?)
        .rerank(Arc::new(lancedb::rerankers::rrf::RRFReranker::default()))
        .limit(2);
    let rows: Vec<RecordBatch> = query.execute().await?.try_collect().await?;
    println!("{rows:?}");

    Ok(())
}
```
</CodeGroup>

The puppy record ranks first because both searches place it first. The query
returns `_relevance_score`, with higher values first. This small example shows
the mechanics; evaluate retrieval quality with embeddings and queries from
your own application.

## Control the candidate results {#query-controls}

Use a result limit, metadata filters and vector distance bounds to control
which candidates are available to the reranker. The examples below show each
option on the query builder.

<Info>
Set `limit()` to the number of results your application needs. The default is 10.
A larger candidate set can help a reranker find relevant records, but adds work.
</Info>

### Returning row IDs {#returning-row-ids}

Pass `with_row_id(True)` (Python) or `withRowId()` (TypeScript) to include the internal `_rowid` column in the results. This is useful for joining hybrid results back to a primary table, or for deduping across multiple queries:

<CodeGroup>
```python Python icon="python"
results = (
    table.search("rebel spaceships", query_type="hybrid")
    .with_row_id(True)
    .limit(10)
    .to_pandas()
)
# results now contains a `_rowid` column alongside `_relevance_score`
```

```typescript TypeScript icon="square-js"
const results = await table
    .query()
    .fullTextSearch("rebel spaceships")
    .nearestTo(queryVector)
    .withRowId()
    .limit(10)
    .toArray();
```
</CodeGroup>

### Bounding vector distance {#bounding-vector-distance}

`distance_range(lower, upper)` (Python) and `distanceRange(lower, upper)` (TypeScript) constrain the vector half of the hybrid query to the half-open interval `[lower, upper)`. This is helpful when you want to cap how far semantic candidates can drift from the query vector before reranking:

<CodeGroup>
```python Python icon="python"
results = (
    table.search("rebel spaceships", query_type="hybrid")
    .distance_range(lower_bound=0.0, upper_bound=0.4)
    .limit(10)
    .to_pandas()
)
```

```typescript TypeScript icon="square-js"
const results = await table
    .query()
    .fullTextSearch("rebel spaceships")
    .nearestTo(queryVector)
    .distanceRange(0.0, 0.4)
    .limit(10)
    .toArray();
```
</CodeGroup>

Either bound can be omitted to leave that side unbounded.

### Prefilter vs. postfilter {#prefilter-vs-postfilter}

A hybrid query applies its metadata filter to both the vector and full-text
searches. Prefiltering, the default, restricts eligible rows before retrieval.
Postfiltering removes candidates after retrieval and can leave fewer results
than requested. See [Filtering](/enterprise/v8-1-0/search/filtering).

<CodeGroup>
```python Python icon="python"
# Prefilter (default): filter applied before scoring
table.search("rebel spaceships", query_type="hybrid") \
    .where("category = 'film'", prefilter=True) \
    .limit(10) \
    .to_pandas()

# Postfilter: filter applied after the sub-queries return top-k
table.search("rebel spaceships", query_type="hybrid") \
    .where("category = 'film'", prefilter=False) \
    .limit(10) \
    .to_pandas()
```

```typescript TypeScript icon="square-js"
// Prefilter (default): just call .where(...)
await table.query()
    .fullTextSearch("rebel spaceships")
    .nearestTo(queryVector)
    .where("category = 'film'")
    .limit(10)
    .toArray();

// Postfilter: chain .postfilter() after .where(...)
await table.query()
    .fullTextSearch("rebel spaceships")
    .nearestTo(queryVector)
    .where("category = 'film'")
    .postfilter()
    .limit(10)
    .toArray();
```
</CodeGroup>

In Python, use [`explain_plan`](/enterprise/v8-1-0/search/explain#analyzing-non-vector-queries) on a hybrid query to see whether the filter pushed into the scan or ran as a separate `FilterExec` step.

## Choose and evaluate a reranker {#more-on-reranking}

Start with RRF, then compare alternatives on representative queries. Review
which relevant rows reach the candidate set before evaluating how a reranker
orders them. Record latency as well as relevance: increasing candidate counts
or applying a model-based reranker adds work.

Reranking runs in the application for both OSS and Enterprise connections.
See [Reranking](/enterprise/v8-1-0/reranking) for model-free fusion, model-based rerankers,
custom implementations and score interpretation.

In synchronous Python, `.rerank(...)` accepts a reranker and a `normalize`
option (`"score"` or `"rank"`). Normalization matters for methods that blend
raw scores; RRF uses rank positions. These are Python query options, not a
shared signature across every SDK.
