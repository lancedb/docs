[LeRobot](https://huggingface.co/docs/lerobot/index) is Hugging Face's open-source robotics stack. Since [lerobot#4363](https://github.com/huggingface/lerobot/pull/4363), `lerobot` reads Lance-formatted datasets natively: the same `LeRobotDataset` class, the same items, the same training pipeline, selected automatically by `"storage_format": "lance"` in the dataset's metadata. No subclasses, no wrapper library.

What that buys you:

- **Train from object storage with a true global shuffle.** Lance reads random frames in place from S3, GCS, HF Hub or HF Storage Buckets, fetching only the byte ranges each batch needs. Upstream's no-download path is a buffered stream: on DROID (27.6M frames) a 230 GB buffer still shuffles 0.15% of the dataset, while Lance shuffles 100% in about 36 GB, at the same throughput, with a first batch in 13 s instead of 7 minutes.
- **Keep the GPUs fed without burning cores.** Lance plans whole batches (one table read, one blob fetch, decoders reused) instead of one frame per call, which is why 4 dataloader workers per rank keep 8xH100 fed where upstream needs 8. Loader throughput in samples/s (8 workers, batch 64), Lance reading from same-region S3 against upstream reading the same data from local disk after a download, and against upstream streaming from the Hub:

| dataset | frames | cameras | Lance, S3 | upstream, local | same job | upstream, streaming | vs streaming |
|---|---|---|---|---|---|---|---|
| DROID | 27,630,375 | 3 | 2,258.5 | 346.7 | 6.5x | 898.6 | 1.7x |
| berkeley_rpt | 392,578 | 1 | 1,740.6 | 1,209.9 | 1.4x | 274.5 | 6.3x |
| toto | 325,699 | 1 | 1,097.0 | 936.3 | 1.2x | 121.3 | 9.0x |
| roboturk | 187,507 | 1 | 1,276.8 | 1,082.3 | 1.2x | 128.2 | 10.0x |
| aloha_mobile_cabinet | 127,500 | 3 | 815.7 | 294.2 | 2.8x | 77.7 | 10.5x |
| koch_pick_place | 37,972 | 2 | 854.7 | 274.9 | 3.1x | 58.1 | 14.7x |

The same-job multiple tracks how much video each sample moves: one camera 1.2x to 1.4x, three cameras 2.8x, DROID 6.5x.

- **Measured end to end.** 10,000 steps of SmolVLA on DROID, 8xH100, lerobot's default `num_workers=4`, same seed and samples on both sides:

| | Lance, S3, nothing downloaded | upstream, local NVMe after a 384 GB download |
|---|---|---|
| wall clock | **1 h 27 m** | 2 h 00 m |
| steady rate | 495 samples/s | 361 samples/s |
| of each step spent waiting on data | 1.7% | 37.4% |
| final loss | 0.2380 | 0.2380 |

The loss curves match to four decimals, so this is one job served two ways, and the 33 minutes are GPU time spent waiting on the loader. That cost scales with the run: at 100,000 steps it is about five and a half hours, every sweep point and re-run pays it again, and a fresh machine adds the download first. It also grows with the dataset, since the multiple follows video volume. Faster accelerators widen it, because the same data wait becomes a larger share of a shorter step.

- **The training table is also the index.** Parquet has row groups and statistics but no secondary indexes, so finding frames instead of scanning them usually means a second system per question: a vector database for embeddings, a search service for instructions, a feature store for scores, each holding its own copy of the truth. With Lance those are columns and indexes on the table the DataLoader reads: scalar indexes on `episode_index`, `task_index` and `video_key` built at conversion, vector and full-text indexes over embedding and instruction columns, derived scores added in place. One query spans all of them, at a pinned version the trainer can reopen.

## Install

```bash
pip install "lerobot[lancedb]"   # the reader, inside lerobot itself
pip install lerobot-lancedb      # the converter
```

## Convert a dataset

Any LeRobot v3.0 dataset, from the Hub or a local directory:

```bash
lerobot-lance-convert --repo-id lerobot/pusht --out ./pusht-lance
```

The output keeps `meta/` unchanged and adds three Lance tables (`frames`, `videos`, `meta`). Videos are stored as blobs without re-encoding, so items are bit-identical to the source and conversion is close to a file copy: 392,578 frames (berkeley_rpt) convert in 10 seconds, DROID's 27.6M in 34 minutes. `lerobot-lance-doctor` audits the result, and regularly finds problems in the source itself: the DROID repo carries 44% orphaned rows that filename-based tooling never notices, and three of eight public datasets we converted have frame-count defects that only random access exposes (shuffled reads crash on any reader, upstream included).

Host the result anywhere: an HF dataset repo (`hf upload`, tag it `v3.0`), an HF Storage Bucket (`hf buckets sync`), or any object store (`aws s3 sync`).

## Load and train

Same class, every location:

<CodeBlock filename="Python" language="Python" icon="python">
  {PyFrameworksLerobotLoad}
</CodeBlock>

An explicit `root` URI works for any object store: `LeRobotDataset("lerobot/pusht", root="s3://my-bucket/pusht-lance")`. Remote roots materialize only `meta/` locally; data is fetched per batch. Everything in the LeRobot training stack works unchanged, including temporal windows and `DataLoader`:

<CodeBlock filename="Python" language="Python" icon="python">
  {PyFrameworksLerobotTrainReady}
</CodeBlock>

Or through the CLI, including held-out evaluation on a remote dataset, which requires random access and is therefore unique to the Lance path:

```bash
lerobot-train \
  --dataset.repo_id=my-org/my-bucket/pusht-lance \
  --dataset.repo_type=bucket \
  --dataset.eval_split=0.02 \
  --policy.type=act
```

## Visualize TB-scale datasets in Foxglove

```bash
lerobot-dataset-viz --repo-id lance-format/pusht-lance --episode-index 3 --display-mode foxglove
```

Connect the Foxglove app to `ws://localhost:8765` and scrub. This serves the episode on demand from wherever the dataset lives: scrubbing an episode of the 373 GB DROID from S3 transfers a few MB, only the frames on screen. No MCAP export, no download.

## Query, curate, enrich

The frames table is a LanceDB table like any other:

<CodeBlock filename="Python" language="Python" icon="python">
  {PyFrameworksLerobotOpenLanceTables}
</CodeBlock>

Filter with SQL over any feature, using the indexes built at conversion:

<CodeBlock filename="Python" language="Python" icon="python">
  {PyFrameworksLerobotFilterFrames}
</CodeBlock>

From here it is standard LanceDB: add columns (embeddings, quality scores, corrected labels) to a TB-scale dataset in place without touching the videos, build vector or full-text indexes over task strings, and drop bad episodes from training with `episodes=[...]` instead of rewriting files. The training reader ignores columns it does not know about, so enrichment and training share one copy of the data.

<Info>
Lance datasets are read-only in LeRobot by design: record and edit in the default format, then convert. The default Parquet/MP4 format on buckets remains streaming-only; map-style remote access is specific to the Lance format.
</Info>

Public examples to try everything above: [`lance-format/pusht-lance`](https://huggingface.co/datasets/lance-format/pusht-lance) and friends under the [`lance-format`](https://huggingface.co/lance-format) org.
