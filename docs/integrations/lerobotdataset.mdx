[LeRobot](https://huggingface.co/docs/lerobot/index) is Hugging Face's open-source robotics stack. Since [lerobot#4363](https://github.com/huggingface/lerobot/pull/4363), `lerobot` reads Lance-formatted datasets natively: the same `LeRobotDataset` class, the same items, the same training pipeline, selected automatically by `"storage_format": "lance"` in the dataset's metadata. No subclasses, no wrapper library.

What that buys you:

- **Train from object storage with a true global shuffle.** Lance reads random frames in place from S3, GCS, HF Hub or HF Storage Buckets, fetching only the byte ranges each batch needs. Upstream's no-download path is a buffered stream: on DROID (27.6M frames) a 230 GB buffer still shuffles 0.15% of the dataset, while Lance shuffles 100% in about 36 GB, at the same throughput, with a first batch in 13 s instead of 7 minutes.
- **Keep the GPUs fed without burning cores.** Lance plans whole batches (one table read, one blob fetch, decoders reused) instead of one frame per call. On DROID that is 6x upstream's map-style throughput at equal workers, and it clears an 8xH100 node's ~880 samples/s demand from local disk at 16 workers. From object storage the budget is bandwidth: about 2.7 GB/s, under a quarter of one 100 GbE link.
- **Measured end to end** (8xH100, SmolVLA on DROID, lerobot's default `num_workers=4`):

| configuration | shuffle | samples/s | GPU data wait | wall clock |
|---|---|---|---|---|
| Lance, S3, nothing downloaded | global, all 27.6M frames | 572 | 1.3% | 252 s |
| Lance, local NVMe | global, all 27.6M frames | 584 | 1.0% | 215 s |
| upstream, local NVMe, after a 412 GB download | global | 362 | 40.2% | 396 s |
| upstream streaming (the no-download path) | windowed, 0.004% | does not run today | | |

The first row is the point: a full global shuffle, read in place from object storage, with the GPUs idle 1.3% of the time. Upstream reaches parity locally by doubling dataloader workers, so the durable difference is CPU cost and the download; the streaming path currently cannot train a multi-GPU language-conditioned policy at all (no per-rank sharding, and batch dispatch rejects the task strings a VLA needs).

- **The training copy is also a database.** Every tabular feature of every frame is one query away, with scalar indexes on `episode_index`, `task_index` and `video_key` built at conversion time. Curation, search, enrichment and EDA run against the same tables the trainer reads.

## Install

```bash
pip install "lerobot[lancedb]"   # the reader, inside lerobot itself
pip install lerobot-lancedb      # the converter
```

## Convert a dataset

Any LeRobot v3.0 dataset, from the Hub or a local directory:

```bash
lerobot-lance-convert --repo-id lerobot/pusht --out ./pusht-lance
```

The output keeps `meta/` unchanged and adds three Lance tables (`frames`, `videos`, `meta`). Videos are stored as blobs without re-encoding, so items are bit-identical to the source. `lerobot-lance-doctor` audits the result, and regularly finds problems in the source itself: the DROID repo, for example, carries 44% orphaned rows that filename-based tooling never notices.

Host the result anywhere: an HF dataset repo (`hf upload`, tag it `v3.0`), an HF Storage Bucket (`hf buckets sync`), or any object store (`aws s3 sync`).

## Load and train

Same class, every location:

<CodeBlock filename="Python" language="Python" icon="python">
  {PyFrameworksLerobotLoad}
</CodeBlock>

An explicit `root` URI works for any object store: `LeRobotDataset("lerobot/pusht", root="s3://my-bucket/pusht-lance")`. Remote roots materialize only `meta/` locally; data is fetched per batch. Everything in the LeRobot training stack works unchanged, including temporal windows and `DataLoader`:

<CodeBlock filename="Python" language="Python" icon="python">
  {PyFrameworksLerobotTrainReady}
</CodeBlock>

Or through the CLI, including held-out evaluation on a remote dataset, which requires random access and is therefore unique to the Lance path:

```bash
lerobot-train \
  --dataset.repo_id=my-org/my-bucket/pusht-lance \
  --dataset.repo_type=bucket \
  --dataset.eval_split=0.02 \
  --policy.type=act
```

## Visualize TB-scale datasets in Foxglove

```bash
lerobot-dataset-viz --repo-id lance-format/pusht-lance --episode-index 3 --display-mode foxglove
```

Connect the Foxglove app to `ws://localhost:8765` and scrub. This serves the episode on demand from wherever the dataset lives: scrubbing an episode of the 373 GB DROID from S3 transfers a few MB, only the frames on screen. No MCAP export, no download.

## Query, curate, enrich

The frames table is a LanceDB table like any other:

<CodeBlock filename="Python" language="Python" icon="python">
  {PyFrameworksLerobotOpenLanceTables}
</CodeBlock>

Filter with SQL over any feature, using the indexes built at conversion:

<CodeBlock filename="Python" language="Python" icon="python">
  {PyFrameworksLerobotFilterFrames}
</CodeBlock>

From here it is standard LanceDB: add columns (embeddings, quality scores, corrected labels) to a TB-scale dataset in place without touching the videos, build vector or full-text indexes over task strings, and drop bad episodes from training with `episodes=[...]` instead of rewriting files. The training reader ignores columns it does not know about, so enrichment and training share one copy of the data.

<Info>
Lance datasets are read-only in LeRobot by design: record and edit in the default format, then convert. The default Parquet/MP4 format on buckets remains streaming-only; map-style remote access is specific to the Lance format.
</Info>

Public examples to try everything above: [`lance-format/pusht-lance`](https://huggingface.co/datasets/lance-format/pusht-lance) and friends under the [`lance-format`](https://huggingface.co/lance-format) org.
